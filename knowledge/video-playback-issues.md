## Симптом

Фоновое промо-видео (`assets/video/shveypro-promo.mp4`, зациклено, со звуком,
16 секунд) периодически на короткое время останавливается вместе со звуком,
затем само продолжает воспроизведение. Проявляется у клиента на её реальном
устройстве; в сэндбоксе агента (headless Chromium) воспроизводится лишь
частично — есть эмпирическое подтверждение ~100-200мс паузы (`seeking` →
`waiting` → `seeked`) ровно в момент зацикливания (на границе 16с), но нет
доступа к реальному устройству/браузеру клиента для полной диагностики.

## Подтверждённые выводы

1. Баг **не связан** с переключателем языков RU/EN/PT и не связан с языковым
   оверлеем на видео (он присутствовал и в чистой RU-версии без оверлея,
   см. попытку 0).
2. Баг **не связан** конкретно с нативным `loop` как механизмом — замена на
   JS-перезапуск ничего не изменила (попытка 3).
3. `will-change`/`translateZ(0)` на зацикленном видео — **подтверждённо вредны**,
   вызывают полную необратимую остановку. Это не теория, а воспроизведённый
   регресс с чистым диффом (единственная разница между «ещё заикается» и
   «умирает навсегда» — ровно эти 3 строки CSS + preload).
4. Снижение битрейта/разрешения само по себе (без GPU-хинтов) не усугубляет
   ситуацию, но и не решает её полностью при текущих настройках.

## Куда НЕ стоит идти снова (проверено, не дало результата или вредно)

- ❌ `transform: translateZ(0)` / `will-change: transform` / `backface-visibility: hidden` на `<video>` с `loop` — ломает видео полностью.
- ❌ `preload="auto"` в сочетании с вышеуказанным (не проверялся изолированно — если захочется попробовать preload отдельно, это НЕ то же самое, что уже проверенная вредная комбинация, но осторожно).
- ❌ Замена нативного `loop` на JS `ended`-рестарт — не меняет ничего.
- ❌ Простое снижение битрейта/разрешения (1080p→720p, 6.5→1.5 Мбит/с) — недостаточно само по себе.

### Автотест попытки №6 (2026-10-05)

Ранее в этом файле было записано, что сэндбокс агента «не декодирует видео в реальном
времени стабильно» (на `chrome-headless-shell`, который использует сам рендерер
hyperframes). Это оказалось верно только для `chrome-headless-shell` — полноценный
headless Chromium через Playwright (`/home/agent/packages/avtomontazh/engine/node_modules/playwright-core`)
декодирует видео стабильно. Тест: локальный статический сервер (те же файлы, что и на
превью-деплое) + Playwright, видео слушается 40 секунд (>2.5 цикла по ~15.3с):
- `MAX_STUCK_RUN_SECONDS: 0` — не было ни одной секунды, когда `currentTime` не продвигался при `paused=false` (а именно так проявлялся фатальный регресс попытки №2 — навсегда).
- Один цикл зацикливания зафиксирован: `seeking → waiting → seeked` заняли ~112мс (t=24079мс → t=24191мс) — короткая пауза в рамках уже известного и принятого клиентом «лёгкого заикания» Version A, не фатальный баг.
- `FINAL_PAUSED: false`, 0 console/page errors.

Это не замена проверке на реальном устройстве клиента (аппаратный decode/композитинг
мог отличаться), но отличная автоматическая регрессия-проверка на будущее — скрипт
лежит в `/tmp/check-video-loop.js` (вне репозитория, можно восстановить по описанию
выше при необходимости повторить).

## Направления, которые ЕЩЁ НЕ пробовали (кандидаты для следующих экспериментов)

- Полное удаление `mask-image`/`-webkit-mask-image` с `<video>` (эффект мягкого
  растворения краёв) — есть теоретическое подозрение, что маска вынуждает
  браузер использовать программный (не аппаратный) путь композитинга видео,
  что дорого по CPU. Не проверялось вживую у клиента, только синтетический
  тест в headless Chromium (неубедительный — сам сэндбокс не декодирует видео
  в реальном времени стабильно, см. заметки в истории задачи).
- Техника двух video-элементов с кроссфейдом в точке склейки (seamless loop)
  — технически более надёжное решение проблемы шва цикла, но требует дублирования
  логики языкового оверлея на оба video-элемента, заметно больше кода.
- Узнать у клиента точный браузер/устройство/ОС, на которых она тестирует —
  сейчас это неизвестно, а без этого трудно направленно диагностировать
  (CPU-decode у слабого устройства vs баг конкретного браузерного движка —
  это разные классы причин с разными решениями).
- Полностью убрать звук/музыку из тестового прогона (отдельный `<video>` без
  audio track) — чтобы изолировать, не является ли причиной именно ресинхронизация
  аудио-дорожки при зацикливании (частая причина в WebKit/Safari).
